# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, no-build, vanilla JS Progressive Web App: "Diageo Sales Presenter". Used in-store on a phone/tablet by a sales rep to (1) build a live drinks order with running totals for a client, (2) track partnership-program tier progress for a store, (3) track call-file visit compliance across a rep's store list, and (4) see that store list plotted on a UK map, colored by visit status. All pages are plain HTML files loaded directly, no bundler. Each rep signs in with their own Firebase account; `localStorage` is still the synchronous state cache every page reads from, but it's now mirrored to a private-per-rep Firestore document in the background — see "Cloud sync (Firebase)" below.

## Running it

There is no build step, package manager, or test suite. To develop:

- Open `index.html` directly in a browser, or serve the folder with any static server (e.g. `python3 -m http.server`) so the service worker and manifest work correctly (service workers require `http://` or `https://`, not `file://`).
- After changing any cached file (JS/CSS/HTML/images in `PRECACHE_URLS`), bump `CACHE_NAME` in [service-worker.js](service-worker.js) — otherwise returning clients keep serving stale cached files.
- The Firebase project is `diageo-sales-presenter`, tied to this repo via `.firebaserc`. `firebase-tools` is already authenticated as `chyakocutz@gmail.com` in this environment — `firebase deploy --only firestore:rules` after editing [firestore.rules](firestore.rules) is the only deploy step; there's no Hosting deploy, the app is still served as plain static files from wherever you put it.

## Architecture

Six pages: `login.html` (signed-out entry point) plus the five signed-in app pages (`index.html`, `products.html`, `partnership.html`, `callfile.html`, `map.html`), sharing a common set of scripts loaded via `<script>` tags (no modules/bundler, with one exception — see below). Load order matters: `catalog.js` and the relevant `layout-*.js` must load before `storage.js`, which must load before the page's own script (`products.js` / `partnership.js` / `callfile.js`), since each builds on globals set by the previous one. `callfile.html` also loads `catalog.js` and `layout-pp.js` (not just `layout-callfile.js`) even though `callfile.js` never edits PP state — it needs `window.CATALOG`/`window.PP_LAYOUT` to render the read-only product grid in the saved-range review modal (see below).

Every app page also loads `js/firebase-config.js` (as `<script type="module">` — the one exception to "no modules," required by the Firebase JS SDK's import syntax) and `js/cloud-sync.js`. Because `type="module"` scripts are deferred, `cloud-sync.js`'s top-level code almost always runs *before* the module has finished — it can't just assume `window.FirebaseAuth` exists. Both `cloud-sync.js` and `js/auth.js` (login.html's script) handle this the same way: check `if (window.FirebaseAuth)`, and if not, `window.addEventListener("firebase-ready", ...)` — `firebase-config.js` fires that event as its last line, after all the `window.FirebaseAuth`/`window.FirebaseDb` globals are set. Since module scripts always execute after every classic script on the page has already run, by the time `firebase-ready` actually fires, `storage.js` (and everything else) is guaranteed to already be loaded — so the exact `<script>` order between `storage.js` and `cloud-sync.js` doesn't matter for correctness, only for readability (kept as storage.js-then-cloud-sync.js, matching the plain load-order rule above).

**Data layering** — each product is defined once and composed across three global objects:
- `window.CATALOG` ([js/catalog.js](js/catalog.js)) — the single source of truth per product: id → `{ name, image, caseSize, bookerPrice, bestwayPrice }`. `caseSize` is used to derive per-bottle price from the case price (case price ÷ caseSize). Wholesaler prices here are placeholders — actual working prices live in `localStorage`, not this file.
- `window.PRODUCTS_LAYOUT` ([js/layout-products.js](js/layout-products.js)) — ordered sections of product ids for the Product Presenter page. Just grouping/ordering, no pricing or coordinates.
- `window.PP_LAYOUT` ([js/layout-pp.js](js/layout-pp.js)) — tier definitions (Tier 1/2/3) for the Partnership Program page. **Core Range is the exact same fixed 17-product list (`CORE_RANGE_TIER3`) for all three tiers** — it's the mandatory "must stock" gate and never widens per tier. What differs per tier is the Bonus/Premium pool stacked on top, which is what grows the required-product target (23 for Tier 3, 25 for Tier 2, 30 for Tier 1). "Core Range" merges what used to be three separate bands (core spirits, Guinness, RTD) into one section, per Diageo's reference diagrams. "Bonus Range" items are flexible either/or slots shown as individually tickable rather than enforced pairs. Each tier's Core Range section carries `isCore: true` — this is a mandatory gate, not just a label (see below), so match on that flag rather than the `label` string, and rather than assuming every tier has the same named sections (Tier 3 has Core Range + Bonus Range; Tier 2 has Core Range + Bonus Range; Tier 1 has Core Range + Bonus Range + Premium Spirits). Every tier's non-core sections carry `promoteOnCheck: true` — see the "jump to Core" note under Partnership Program below. Tier 3 also carries `unlockCount: 20` — see the reward-threshold note below.
- `window.CALLFILE_GRADES` / `window.CALLFILE_GRADE_CONFIG` ([js/layout-callfile.js](js/layout-callfile.js)) — the three store grades (display order: Platinum, Gold, Silver) and their fixed visit rule: `cadenceWeeks` (how often a store is due) and `visitsRequired` (visits needed in a calendar month to go green). Platinum = 2 weeks / 2 visits; Gold and Silver = 4 weeks / 1 visit each. This is a deliberate override of the uploaded sheet's own `FREQUENCY`/`VISITCADENCE` columns (which put Silver at 8 weeks) — the business rule here always wins over whatever the export says.

**State** — [js/storage.js](js/storage.js) is the only module that touches `localStorage`, under key `diageoPresenter` with a `SCHEMA_VERSION` (currently 5). It distinguishes:
- Persisted across resets: `prices` (per-product, per-wholesaler case prices), `targetCounts` (per-tier required-product counts), and `callfile` (uploaded stores + their visit history) — all user-edited.
- Session-only, cleared by each page's "Reset" button (Call File has no reset button — there's nothing to reset, visit history is meant to persist): `productsSession` (quantities, units, active wholesaler), `ppSession` (active tier, checked products), and `callfileSession` (active grade tab — persists across reloads but isn't cleared by a reset flow).

The `prices` shape and `activeWholesaler`/`setActiveWholesaler` machinery still support both `booker` and `bestway` keys, but **Product Presenter's wholesaler selector UI has been removed** — `products.js` now hardcodes `"booker"` everywhere it used to read `productsSession.activeWholesaler`, so the app only ever prices/edits Booker case prices even though the underlying state shape wasn't changed (kept as-is to avoid a `SCHEMA_VERSION` bump for a UI-only change).

If `parsed.version !== SCHEMA_VERSION`, `loadState()` discards saved data entirely and falls back to defaults — bump `SCHEMA_VERSION` in the same commit as any shape change to `defaultState()`, and be aware this wipes all users' saved prices/targets/call file *on that device*. It does not touch Firestore — the next successful `saveState()` (or the next page load's cloud hydration) re-syncs the two, so a `SCHEMA_VERSION` bump is a purely local reset, not a data-loss event for cloud-synced reps. `version` itself is never sent to Firestore; only `prices`/`targetCounts`/`callfile` are (see below).

**Cloud sync (Firebase)** — each rep has their own Firebase Authentication account (email/password, self-service signup on [login.html](login.html)/[js/auth.js](js/auth.js)) and their own Firestore document at `users/{uid}`, holding exactly the *persisted* slice of state — `{ prices, targetCounts, callfile }` — the same fields already described above as "persisted across resets." Session-only state (`productsSession`, `ppSession`, `callfileSession`) never leaves the device, same as before Firebase existed.
- **Design goal**: keep every existing page script (`products.js`/`partnership.js`/`callfile.js`) completely synchronous and untouched. `localStorage` remains the only thing `Storage.loadState()` reads, so `render()` still works exactly as it always has, including fully offline. Firestore is purely a background mirror underneath it, added in [js/cloud-sync.js](js/cloud-sync.js) and two small hooks in [js/storage.js](js/storage.js).
- **Writes**: `saveState()` (the one choke point every `Storage.set*`/`import*`/`log*`/`save*` mutator already funnels through) now also calls `window.CloudSync.pushState(state, callfileChanged)` — fire-and-forget from `storage.js`'s point of view (`.catch`'d to `console.error` rather than surfaced to the rep, since a failed background sync shouldn't block them from continuing to work locally), but internally `cloud-sync.js` chains every push onto a single `pushChain` promise rather than firing `setDoc` calls independently. This matters specifically for a Platinum store: it's the only grade where a rep logs two visits for the same store close together (Gold/Silver only ever need one), which fires two unawaited writes seconds apart — over patchy in-store wifi, without chaining, the *older* 1-visit write can arrive at Firestore *after* the newer 2-visit one and silently overwrite it, since the server just applies whichever write it receives last regardless of timestamp. Chaining guarantees the 2nd write's network request isn't even sent until the 1st has finished, so Firestore always receives them in the order they actually happened. `callfileChanged` is an optional bool the specific mutation passes when it touched `callfile` (e.g. `logVisit`/`addStore`/`deleteStore`/`importCallfile`/etc. all pass `true`; `setPrice`/`toggleChecked`/etc., which never touch the call file, pass nothing). `pushState` always pushes `prices`/`targetCounts` in full, and only ever includes `callfile` in the write when `callfileChanged` is true — but when it does, it pushes the *entire* `state.callfile` object (not a per-store patch), written with `setDoc(ref, payload, { mergeFields: [...] })`. `mergeFields` (naming which top-level fields the payload provides) is what keeps this safe on two fronts at once: it leaves `prices`/`targetCounts` untouched when only `callfile` changed (and vice versa), while still replacing the *entire* `callfile` field with exactly what's given — including dropping any store key no longer present locally — rather than `{merge: true}`'s recursive deep-merge, which would leave a locally-deleted store's key alive forever on the server.
- **Reads / hydration**: on load, `cloud-sync.js` waits for Firebase auth state (redirecting to `login.html` if signed out — this is the auth guard), then `getDoc`s the rep's `users/{uid}` doc once. If it exists, `Storage.hydrateFromCloud(cloudDoc)` writes `prices`/`targetCounts` straight from the cloud doc into the local blob (bypassing `saveState()`/`pushState()` — this data came *from* the cloud, echoing it back would be pointless), and, since this all happens asynchronously after the page's first synchronous `render()` has already run once against whatever was locally cached, calls the page's global `render()` again (`typeof window.render === "function"`) so the UI catches up. It then opens a live `onSnapshot` listener on the same doc (skipping events where `metadata.hasPendingWrites` is true, since those are just this tab's own writes echoing back) so a second device's changes show up without a manual refresh.
- **First login** (`users/{uid}` doesn't exist yet): if `Storage.hasSavedData()` says this device already has a local blob, `confirm()` before adopting it as the new account's starting point; otherwise (or if declined) the account starts from `Storage.defaultPersistedSlice()` — the same defaults a brand-new device would have.
- **Isolation**: enforced by [firestore.rules](firestore.rules) — `allow read, write: if request.auth.uid == uid`, nothing else. There's no shared/team data; every rep's `prices`/`targetCounts`/`callfile` are theirs alone, matching the fully-private-per-rep decision this was built around.
- **Conflict handling** for `prices`/`targetCounts` is last-write-wins (whichever `setDoc` lands on Firestore last simply overwrites those fields) — a deliberate simplification, acceptable because data is private per rep (no simultaneous multi-user editing of the same doc to reconcile), not because it's the "correct" general solution. `callfile` uses the same last-write-wins idea, just gated on its own single `callfile.updatedAt` timestamp (bumped by every store mutator: `logVisit`/`resetVisits`/`resetAllVisits`/`addStore`/`updateStore`/`deleteStore`/`importCallfile`/`savePPSnapshot`) rather than the top-level fields' implicit "whichever write landed last" — `Storage.hydrateFromCloud()` compares `state.callfile.updatedAt` (local) against the incoming `slice.callfile.updatedAt` and adopts the incoming `callfile` *wholesale* only if it's at least as new; otherwise local is left alone (a rep can navigate to another page, or switch browsers, before a just-made change like logging a visit has actually finished pushing to Firestore — without this, the next page's own hydration read could race that in-flight write and roll the visit back). Every callfile saved before `updatedAt` existed lacks the field entirely (`undefined`, not `""`) — `hydrateFromCloud()` treats "neither side has one" as nothing-to-compare and leaves local alone rather than a bare `"" >= ""` string comparison, which would (and initially did) make the cloud unconditionally win on *every* hydration until some mutation finally stamps a real timestamp on either side, permanently masking whatever the fix itself changed. The one exception is a genuinely fresh device with no locally-cached stores at all, which has nothing to lose by adopting the cloud's copy even if it's also unstamped — the normal first-sync case. Earlier versions of this tried a *per-store* merge (each store keeping its own `updatedAt`, deletions written as tombstones so a stale read couldn't resurrect them) to let two devices' *different* stores merge without either clobbering the other — in practice this was a recurring source of bugs (a store rendered from a hybrid of an old cloud copy and a newer local one), so it was replaced with the simpler whole-`callfile` swap described above. The accepted tradeoff: if two sessions (e.g. this app open in both Chrome and Safari on the same phone) each edit a *different* store within the same few seconds, before either has synced, the one that pushes second wins outright and the other's edit is lost — including a store deletion: a stale session that still has a since-deleted store cached locally and pushes for an unrelated reason (e.g. logging a visit elsewhere) will resurrect it, since the whole `stores` map goes out together. Acceptable because actual usage is one rep working in one browser/device at a time (each page load re-hydrates from Firestore before any mutation can happen, which is what keeps this rare in practice), not simultaneous editing across two. `Storage.liveStoreKeys(stores)`/`Storage.getLiveStore(stores, key)` are still the two helpers every consumer (`callfile.js`, `map.js`, `partnership.js`'s store picker, `home.js`) reads `callfile.stores` through — now thin wrappers with no tombstone-filtering to do, kept so those call sites didn't need to change.

**Page scripts** ([js/products.js](js/products.js), [js/partnership.js](js/partnership.js), [js/callfile.js](js/callfile.js)) each follow the same pattern: a pure `render()` that reads `Storage.loadState()` and the relevant layout/catalog to rebuild the DOM from scratch (via `innerHTML` string templates, not diffing), plus a single delegated click listener per container keyed off `data-action`/`data-id` attributes. There's no framework — every UI update goes through a full `render()` call.

**Poster-matched theme (Partnership Program)** — `partnership.js`'s `render()` also sets `#tier-hero-img`'s `src` from a `HERO_IMAGES` map to show that tier's poster image, and sets `#tier-panel`'s class to `theme-silver` (Tier 3/1) or `theme-gold` (Tier 2). `css/styles.css` reads those theme classes to color the `.category` bands so the checklist visually matches the poster shown above it.

**Core Range gating (Partnership Program)** — Core Range is the mandatory "must stock" baseline, so a tier can't reach its reward threshold on Bonus/Premium items alone. `coreStats()` in `partnership.js` finds the section with `isCore: true` and checks whether every item in it is ticked; `tierStats()` folds this in as `pct = gatesComplete ? realPct : Math.min(realPct, 89)` — the displayed percentage itself is capped at 89%, not just the celebration badge, whenever a gate is incomplete. The Core Range `<h3>` also gets a live `.core-status` tag (amber `checked/total`, or green "✓ Complete") so the rep can see what's blocking the reward. This has no persisted state — it's pure derived math from `ppSession.checked`, recomputed on every `render()`.

**Reward unlock threshold (Partnership Program)** — Tier 1 and Tier 2 unlock their reward at 90%+ of the required count (`realPct >= 90`, on top of the gates above). Tier 3 instead unlocks at an **absolute count** — `unlockCount: 20` (of 23) in `layout-pp.js` — because 90% of 23 rounds up to 21, which is stricter than the intended "20 of 23" rule. `tierStats()` computes `unlocked` from whichever rule the tier's `unlockCount` field implies, and `render()` builds the `tier-reward` line's "at X" wording (`"20 of 23"` vs `"90%+ of 25"`) and drives the celebration badge (`isCelebrating = stats.unlocked`) from the same flag, so the two tier types can't drift apart. A tier without `unlockCount` always falls back to the 90% rule.

Gating isn't limited to "100% of Core Range" — a section can instead carry `gate: { groups: [{ label, items, min }, ...] }` for a partial (N-of-M) requirement, checked by `sectionGateStats()`. Currently only Tier 3's Bonus Range uses this: at least 2 of its 4 "bottle" items AND 1 of its 2 "crush" items must be ticked, on top of (not instead of) Core Range being 100% stocked — `tierStats()`'s `gatesComplete` ANDs every section's gate (isCore or quota-based) together. `gateTagHtml()` renders whichever tag applies per section (Core Range's is-core tag, or a quota section's `label checked/total` breakdown), and `gateSummaryText()` builds the `tier-reward` line's parenthetical from the tier's actual gates so it can't drift out of sync with `layout-pp.js`.

**"Jump to Core" display (Partnership Program)** — a section with `promoteOnCheck: true` (every tier's Bonus Range/Premium Spirits sections) visually promotes its ticked items into the Core Range section instead of leaving them in place: `sectionItemsToRender()` hides checked items from their own `promoteOnCheck` section and `jumpedItems()` appends them into the Core Range section's render list, tagged with a small "Bonus" badge (`isJumped` in `tileHtml()`). This is **purely cosmetic** — `coreStats()`/`tierStats()`/`gateTagHtml()` still read only the section's fixed `items` list, so the Core-100% gate always means exactly the 17 `CORE_RANGE_TIER3` products no matter what's ticked elsewhere. Unticking a jumped item sends it back down to its original section on the next `render()`. A `promoteOnCheck` section that empties out (everything jumped) is skipped entirely by `sectionHtml()` (returns `null`, filtered out) rather than showing a bare header. `Storage.selectAllTier()` bulk-ticks every item in the active tier at once (the "Select all" button, confirmed via `confirm()` since there's no per-tier undo — only the all-tiers Reset).

**Product zoom modal (Partnership Program)** — tapping a tile anywhere outside its "In stock" tick row (via `#tier-sections`'s delegated click listener falling through to `.pp-tile` when `.tick-row` doesn't match) calls `openProductModal(id)`, which sets in-memory `ppUi.zoomId` and re-renders. `renderModal()` (called at the end of every `render()`) shows/hides `#product-modal` and fills it from `window.CATALOG` plus a local `casePriceFor()`/`formatMoney()` (small copies of `products.js`'s helpers, always reading the Booker price, since `products.js` isn't loaded on this page). The modal has its own "In stock" toggle wired to the same `Storage.toggleChecked()`, so ticking from inside it updates the underlying grid too. Closes via the × button, tapping the backdrop, `Escape`, or switching tiers (`ppUi.zoomId` is reset alongside `ppUi.wasAbove90` in the tier-tab click handler). `ppUi.zoomId` is session-only UI state, never persisted.

**Save range to Call File (Partnership Program → Call File)** — the "Save to Call File" button lets a rep freeze the current tier's checklist state onto a specific store, so it can be reviewed later from Call File. There's no notion of "which store you're currently at" anywhere else in the app (Products/Partnership are just a global session), so saving always goes through a store picker: `openStorePicker()` sets `ppUi.storePickerOpen` and `renderStorePicker()` shows `#store-picker-modal`, a searchable list built the same way as Call File's own store search. Tapping a store builds a snapshot — `{ date, tierKey, checkedIds, checkedCount, target, pct, unlocked }`, where `checkedIds` comes from `tierCheckedIds()` (every item across the active tier's sections that's ticked in `ppSession.checked`) — and calls `Storage.savePPSnapshot(key, snapshot)`. `ppSession` itself is untouched by saving (non-destructive, no auto-reset). `savePPSnapshot()` `unshift`s onto that store's `ppHistory` array and slices to the 2 most recent (newest first) — deliberately capped, not unlimited history. `Storage.importCallfile()` carries `ppHistory` forward from the prior record on re-upload, the same way it already does for `visits`, so re-uploading a call file export doesn't wipe saved ranges.

On the Call File side, a store card only shows a "Range" button when `store.ppHistory.length > 0` (keeps the compact two-line store-card layout for stores with nothing saved). Tapping it calls `openRangeModal(key)`, which sets `callfileUi.rangeKey`/`rangeIndex` and shows `#range-modal`: up to 2 tappable date tabs (one per snapshot) plus a detail pane built by `snapshotSectionsHtml()`, which walks `window.PP_LAYOUT[snapshot.tierKey].sections` and renders each section's fixed `items` list against `snapshot.checkedIds` — deliberately **not** replicating the "jump to Core" promotion (`promoteOnCheck`) since that's a live-editing cosmetic feature a frozen historical view doesn't need. The tiles (`snapshotTileHtml()`) are read-only copies of `partnership.js`'s `tileHtml()` with no click handlers. `callfileUi.rangeKey`/`rangeIndex` are session-only UI state, never persisted.

**Call File** ([js/callfile.js](js/callfile.js), [callfile.html](callfile.html)) — lets a rep upload their call-file export (`.xls`/`.xlsx`/`.csv`, parsed client-side via the vendored [js/vendor/xlsx.full.min.js](js/vendor/xlsx.full.min.js) — SheetJS, since there's no package manager to pull it in another way) and track monthly visit compliance per store.
- Only `OUTLETNAME` / `OUTLETGRADE` / `POSTCODE` are read from the sheet; everything else (DIAGEOID, FREQUENCY, VISITCADENCE, TERRITORY, ...) is ignored by design.
- Stores are keyed by a normalized `name|postcode` string (`Storage.storeKey`), not a spreadsheet id — re-uploading a later export matches existing stores by that key and keeps their visit history. Duplicate rows sharing name+postcode within one upload collapse to a single store (last row in the file wins); there's no DIAGEOID to tell a true duplicate apart from two different accounts that coincidentally share a name+postcode, so `Storage.importCallfile` reports how many rows collapsed (`duplicateCount`) rather than silently guessing.
- Status colour is *derived at render time*, never stored: `storeStatus()` (in [js/callfile-status.js](js/callfile-status.js), shared with `map.js` — see Map below, rather than living privately in `callfile.js`) counts how many dates in a store's `visits` array fall in the current calendar month and compares against `CALLFILE_GRADE_CONFIG[grade].visitsRequired`. This is what makes the "every store goes back to red at the start of a new month" behavior automatic — there's no reset job, it just falls out of the date math. Visits are never deduped by date (`Storage.logVisit`), since a Platinum store can legitimately be visited twice in one day and both must count.
- The grade tabs (Platinum/Gold/Silver, one visible at a time) are a UI-only filter — `callfileSession.activeGrade` just controls which pre-computed group is rendered.
- **Store list UI** — `.store-list` is a bordered, internally-scrolling panel (`max-height` + `overflow-y: auto`) rather than an unbounded page section, so a large call file doesn't turn the page itself into one long scroll. Each `.store-card` is a compact two-line layout (`storeRowHtml()`): name + status pill on top, postcode/last-visit/next-visit + the "Log visit" button on the bottom. `statusLabel()` and the dates (`formatDateShort()`, no year) are deliberately terse to fit that one line without wrapping.
- **Log-a-visit date picker** — tapping "Log visit" no longer logs `todayISO()` immediately; it calls `openVisitModal(key)`, which sets in-memory `callfileUi.logKey` and re-renders to show `#visit-modal` (same `.modal-backdrop`/`.modal-card` pattern as the PP product modal) with a native `<input type="date">` defaulted to today and capped (`max`) at today so a rep can't log a future visit, but *can* back-date a forgotten visit. `renderVisitModal()` (called at the end of every `render()`) just shows/hides the modal and fills in the store name — it never touches the date input's value, so an in-progress date pick survives re-renders. Confirming reads the input's value and calls `Storage.logVisit(key, dateVal, cfg.cadenceWeeks)` with that chosen date instead of today's. Closes via the × button, backdrop click, `Escape`, or Cancel, all funneling through `closeVisitModal()`. `callfileUi.logKey` is session-only UI state, never persisted.

**Map** ([js/map.js](js/map.js), [map.html](map.html)) — plots every Call File store with a postcode as a pin on a real, pannable UK map, colored by the same `storeStatus()` red/amber/green rule Call File uses (they share [js/callfile-status.js](js/callfile-status.js) — `todayISO()`/`storeStatus()`/`statusLabel()` were extracted out of `callfile.js` into that file specifically so this page and Call File can't drift on the business rule). `callfile.js` itself is *not* loaded on `map.html` — its `DOMContentLoaded` handler assumes callfile.html's DOM (`#store-list` etc.) exists, so map.js only pulls in the shared status file plus `layout-callfile.js` for `CALLFILE_GRADE_CONFIG`.
- **Map library** — Leaflet is vendored locally at `js/vendor/leaflet/leaflet.js`/`leaflet.css` (same treatment as `js/vendor/xlsx.full.min.js`), tiles are fetched at runtime from OpenStreetMap and are deliberately *not* in `PRECACHE_URLS` (cross-origin, dynamic per pan/zoom — same opportunistic-cache-only tradeoff already accepted for the Firebase SDK). Markers are `L.circleMarker`s (colored SVG dots via `fillColor`), not Leaflet's default image-based `L.Icon`, so no marker-icon PNGs need vendoring.
- **Geocoding** — postcodes are raw, unvalidated strings straight off the uploaded sheet (`callfile.js`'s `parseWorkbook()`), so `map.js` geocodes them at runtime via the free, no-key **postcodes.io** bulk endpoint (`POST https://api.postcodes.io/postcodes`, chunked into batches of 100 — its per-request limit) and caches both hits and misses (`{found:false}`) in a **separate** localStorage key, `diageoGeocodeCache` — deliberately *not* part of the schema-versioned `diageoPresenter` blob, since geocoded coordinates are derived reference data, not private per-rep state, so they don't need a `SCHEMA_VERSION` bump or Firestore sync. The cache key is the normalized postcode string itself, so a rep fixing a typo'd postcode in a re-uploaded call file automatically gets a fresh cache entry with no manual invalidation.
- **Re-render safety** — `render()` is called on `DOMContentLoaded` and, since it's an implicit `window.render` (a top-level classic-script function declaration, same as every other page's `render()`), also by `cloud-sync.js`'s post-hydration/`onSnapshot` re-render hook. Three module-level `mapState` flags make repeat calls safe: `ensureMap()` no-ops after the first `L.map()` call (Leaflet throws if you initialize the same container twice), `hasFitBounds` stops the view from re-centering after the rep has already panned/zoomed, and `inFlightPostcodes` dedupes concurrent geocode requests for the same postcode.
- **Status colors** are read from `--good`/`--warn`/`--bad` via `getComputedStyle` at map-init time rather than hardcoded — Leaflet's SVG renderer sets `fill` as a raw attribute, which can't resolve `var(--good)` directly, so this keeps the map palette tied to Call File's pill/dot colors without a second copy of the hex values.
- Tapping a pin shows a read-only popup (name/grade/postcode/status/last & next visit) — no "log a visit" action from the map; that stays on Call File. There's no grade-tab filter (unlike Call File) — all grades show at once with a status legend, since the tabs exist there to keep a long scrollable list short, which doesn't apply to an overview map.

**Nav/shell** — [js/nav.js](js/nav.js) injects the shared header into every page (called as `renderNav("home"|"products"|"partnership"|"callfile"|"map")` from an inline `<script>` at the bottom of each HTML file) and registers the service worker. It is the only place that knows the page list. It also renders the signed-in rep's email and a "Log out" button — filled in once `onAuthStateChanged` resolves (same `firebase-ready` handshake as everywhere else Firebase is used), since the header itself renders before auth state is known. `login.html` doesn't call `renderNav()` at all — it isn't part of the app shell.

**Offline support** — [service-worker.js](service-worker.js) is cache-first: it precaches an explicit file list (`PRECACHE_URLS`, including product images, the `images/PP/tier-*.png` poster images, and the vendored xlsx library) on install, serves from cache first on fetch, and falls back to network only on cache miss. On activate it deletes any cache not matching the current `CACHE_NAME`. Because of this, a browser that already has the app open needs a hard refresh (or full close/reopen if installed as a home-screen PWA) to pick up a new `CACHE_NAME` — bumping the constant alone doesn't update already-open clients. The Firebase SDK itself is fetched from `www.gstatic.com` at runtime and is *not* in `PRECACHE_URLS` (a cross-origin precache failure would fail the entire service worker install) — it's cached opportunistically by the same cache-first `fetch` handler after its first successful load, so a rep who's opened the app online at least once can still open it (and read their last-synced local data) offline; signing in for the very first time still requires a live connection.
