# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, no-build, vanilla JS Progressive Web App: "Diageo Sales Presenter". Used in-store on a phone/tablet by a sales rep to (1) build a live drinks order with running totals for a client, (2) track partnership-program tier progress for a store, (3) track call-file visit compliance across a rep's store list, (4) see that store list plotted on a UK map, colored by visit status, and (5) log per-product stock-status answers on every cash & carry (C&C) depot visit, mirroring an external Microsoft Form. All pages are plain HTML files loaded directly, no bundler. Each rep signs in with their own Firebase account; `localStorage` is still the synchronous state cache every page reads from, but it's now mirrored to a private-per-rep Firestore document in the background — see "Cloud sync (Firebase)" below.

## Running it

There is no build step, package manager, or test suite. To develop:

- Open `index.html` directly in a browser, or serve the folder with any static server (e.g. `python3 -m http.server`) so the service worker and manifest work correctly (service workers require `http://` or `https://`, not `file://`).
- After changing any cached file (JS/CSS/HTML/images in `PRECACHE_URLS`), bump `CACHE_NAME` in [service-worker.js](service-worker.js) — otherwise returning clients keep serving stale cached files.
- The Firebase project is `diageo-sales-presenter`, tied to this repo via `.firebaserc`. `firebase-tools` is already authenticated as `chyakocutz@gmail.com` in this environment — `firebase deploy --only firestore:rules` after editing [firestore.rules](firestore.rules) is the only Firebase deploy step. The static files themselves are hosted on **Vercel** (pushed to GitHub, Vercel builds from the repo): [vercel.json](vercel.json) sets the HTTP security headers (CSP, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, ...) and [.vercelignore](.vercelignore) keeps `CLAUDE.md`/`DESIGN.md`/`PRODUCT.md`/`firestore.rules`/`.firebaserc`/any `*.xls` out of the deployed site — add any new internal-only file there too.
- **No inline scripts.** Every page carries a `<meta http-equiv="Content-Security-Policy">` (a copy of the `vercel.json` header, so the policy also applies when the files are served from anywhere else, e.g. a local `http.server`) whose `script-src` is `'self' https://www.gstatic.com` — an inline `<script>` block is silently blocked. Pages bootstrap their nav via `<script src="js/nav.js" data-page="callfile">` (see Nav/shell below), not `<script>renderNav("callfile")</script>`. If you add a new external origin (a CDN, an API), it has to be added to **both** the `vercel.json` header and every page's meta tag, in the right directive (`script-src` / `connect-src` / `img-src`). Inline `style=""` attributes are allowed (`style-src 'unsafe-inline'`) because the string templates and Leaflet rely on them. **The header applies to `service-worker.js` too**, and a worker's own `fetch()` is governed by *its* `connect-src` — so every cross-origin host the worker fetches on a page's behalf (`www.gstatic.com/firebasejs/*` and `*.tile.openstreetmap.org`, i.e. `RUNTIME_CACHE_ORIGINS`) must be in `connect-src` as well as the directive the page needs (`script-src`/`img-src`). Missing that gave a grey map with dots but no tiles, and only on devices where the worker was already in control: a first page load isn't worker-controlled, so a plain load test passes — reproduce with a second, controlled load (or the scratchpad `swtest` harness). Any fix to the worker's policy also needs a `CACHE_NAME` bump, since an installed worker keeps the header it was fetched with until the script's bytes change. `img-src` also allows the single URL `https://www.google.com/images/cleardot.gif` — the Firestore SDK's WebChannel transport loads that 1×1 GIF as a connectivity probe when it thinks the network dropped, and blocking it showed up as a CSP violation in the offline/online end-to-end test.
- The rules test harness lives outside the repo: `@firebase/rules-unit-testing` + the Firestore emulator (needs a Java runtime) run against `firestore.rules` — see the "Isolation" note under Cloud sync for what it covers. Rerun it after any rules change.

## Architecture

Seven pages: `login.html` (signed-out entry point) plus the six signed-in app pages (`index.html`, `products.html`, `partnership.html`, `callfile.html`, `map.html`, `cashcarry.html`), sharing a common set of scripts loaded via `<script>` tags (no modules/bundler, with one exception — see below). Load order matters: `catalog.js` and the relevant `layout-*.js` must load before `js/state-shape.js`, which must load before `storage.js`, which must load before the page's own script (`products.js` / `partnership.js` / `callfile.js`), since each builds on globals set by the previous one. `js/nav.js` is always the **last** script tag (it moves everything already in `<body>` into the sidebar shell — see Nav/shell). `callfile.html` also loads `catalog.js` and `layout-pp.js` (not just `layout-callfile.js`) even though `callfile.js` never edits PP state — it needs `window.CATALOG`/`window.PP_LAYOUT` to render the read-only product grid in the saved-range review modal (see below).

Every app page also loads `js/firebase-config.js` (as `<script type="module">` — the one exception to "no modules," required by the Firebase JS SDK's import syntax) and `js/cloud-sync.js`. Because `type="module"` scripts are deferred, `cloud-sync.js`'s top-level code almost always runs *before* the module has finished — it can't just assume `window.FirebaseAuth` exists. Both `cloud-sync.js` and `js/auth.js` (login.html's script) handle this the same way: check `if (window.FirebaseAuth)`, and if not, `window.addEventListener("firebase-ready", ...)` — `firebase-config.js` fires that event as its last line, after all the `window.FirebaseAuth`/`window.FirebaseDb` globals are set. Since module scripts always execute after every classic script on the page has already run, by the time `firebase-ready` actually fires, `storage.js` (and everything else) is guaranteed to already be loaded — so the exact `<script>` order between `storage.js` and `cloud-sync.js` doesn't matter for correctness, only for readability (kept as storage.js-then-cloud-sync.js, matching the plain load-order rule above).

**Data layering** — each product is defined once and composed across three global objects:
- `window.CATALOG` ([js/catalog.js](js/catalog.js)) — the single source of truth per product: id → `{ name, image, caseSize, bookerPrice, bestwayPrice }`. `caseSize` is used to derive per-bottle price from the case price (case price ÷ caseSize). Wholesaler prices here are placeholders — actual working prices live in `localStorage`, not this file.
- `window.PRODUCTS_LAYOUT` ([js/layout-products.js](js/layout-products.js)) — ordered sections of product ids for the Product Presenter page. Just grouping/ordering, no pricing or coordinates.
- `window.PP_LAYOUT` ([js/layout-pp.js](js/layout-pp.js)) — tier definitions (Tier 1/2/3) for the Partnership Program page. **Core Range is the exact same fixed 17-product list (`CORE_RANGE_TIER3`) for all three tiers** — it's the mandatory "must stock" gate and never widens per tier. What differs per tier is the Bonus/Premium pool stacked on top, which is what grows the required-product target (23 for Tier 3, 25 for Tier 2, 30 for Tier 1). "Core Range" merges what used to be three separate bands (core spirits, Guinness, RTD) into one section, per Diageo's reference diagrams. "Bonus Range" items are flexible either/or slots shown as individually tickable rather than enforced pairs. Each tier's Core Range section carries `isCore: true` — this is a mandatory gate, not just a label (see below), so match on that flag rather than the `label` string, and rather than assuming every tier has the same named sections (Tier 3 has Core Range + Bonus Range; Tier 2 has Core Range + Bonus Range; Tier 1 has Core Range + Bonus Range + Premium Spirits). Every tier's non-core sections carry `promoteOnCheck: true` — see the "jump to Core" note under Partnership Program below. Tier 3 also carries `unlockCount: 20` — see the reward-threshold note below.
- `window.CALLFILE_GRADES` / `window.CALLFILE_GRADE_CONFIG` ([js/layout-callfile.js](js/layout-callfile.js)) — the three store grades (display order: Platinum, Gold, Silver) and their fixed visit rule: `cadenceWeeks` (how often a store is due) and `visitsRequired` (visits needed in a calendar month to go green). Platinum = 2 weeks / 2 visits; Gold and Silver = 4 weeks / 1 visit each. This is a deliberate override of the uploaded sheet's own `FREQUENCY`/`VISITCADENCE` columns (which put Silver at 8 weeks) — the business rule here always wins over whatever the export says.

**State** — [js/storage.js](js/storage.js) is the only module that touches `localStorage`, under key `diageoPresenter` with a `SCHEMA_VERSION` (currently 7). It distinguishes:
- Persisted across resets: `prices` (per-product, per-wholesaler case prices), `targetCounts` (per-tier required-product counts), `callfile` (uploaded stores + their visit history), and `cashCarry` (the single remembered Cash & Carry Form draft — see below) — all user-edited.
- Session-only, cleared by each page's "Reset" button (Call File has no reset button — there's nothing to reset, visit history is meant to persist): `productsSession` (quantities, units, active wholesaler), `ppSession` (active tier, checked products), and `callfileSession` (active grade tab — persists across reloads but isn't cleared by a reset flow). `cashCarry` has no session-only counterpart at all — unlike every other feature, the entire point is that it's remembered indefinitely with nothing to reset.

The `prices` shape and `activeWholesaler`/`setActiveWholesaler` machinery still support both `booker` and `bestway` keys, but **Product Presenter's wholesaler selector UI has been removed** — `products.js` now hardcodes `"booker"` everywhere it used to read `productsSession.activeWholesaler`, so the app only ever prices/edits Booker case prices even though the underlying state shape wasn't changed (kept as-is to avoid a `SCHEMA_VERSION` bump for a UI-only change).

**Shape validation** ([js/state-shape.js](js/state-shape.js), `window.StateShape`) — every blob `storage.js` reads, from `localStorage` in `loadState()` or from a Firestore snapshot in `hydrateFromCloud()`, goes through `sanitizePersistedSlice()` first (and the session-only sub-objects through `sanitizeProductsSession`/`sanitizePpSession`/`sanitizeCallfileSession`). Every page's `render()` dereferences state with plain property access (`store.visits.filter(...)`, `store.ppHistory.length`), so one malformed store — an interrupted write, an older shape, a stray console edit — used to throw on every page load with no way for the rep to recover short of clearing site data. The policy is: coerce where the sane value is obvious (a numeric-string price, a missing array becomes `[]`, a non-ISO visit date is dropped), and **drop the record** where it isn't (a store with no name or a grade outside `CALLFILE_GRADES` can't be displayed or counted, so keeping it just moves the crash downstream). `sanitizePersistedSlice()` preserves key *presence* (only keys actually in the input come back), which is what lets `hydrateFromCloud()` use `"repTerritory" in slice` to propagate a territory cleared to `null` on another device — a truthiness check would ignore it. `manager-cloud.js` runs every rep's `callfile` through `sanitizeCallfile()` too, since a single bad store in any one rep's doc would otherwise take down the whole cross-rep dashboard/map for every manager. `logVisit`/`logCcVisit`/`logCycleBrief` refuse a non-`YYYY-MM-DD` date outright (`StateShape.isDate`) rather than half-applying a visit and throwing in the `nextVisitDate` math. Verified with a Node harness (stubbed `localStorage`/`window`, real `storage.js`) feeding malformed blobs — keep that passing when touching either file.

**Guarded writes** — `localStorage.setItem` can throw (quota exceeded, Safari private mode, storage disabled). `storage.js`'s `writeLocal()` wraps every write: a failure is `console.warn`ed and the mutation continues, so `saveState()` still pushes the change to Firestore even when the device refused to cache it locally.

If `parsed.version !== SCHEMA_VERSION`, `loadState()` discards saved data entirely and falls back to defaults — bump `SCHEMA_VERSION` in the same commit as any shape change to `defaultState()`, and be aware this wipes all users' saved prices/targets/call file *on that device*. It does not touch Firestore — the next successful `saveState()` (or the next page load's cloud hydration) re-syncs the two, so a `SCHEMA_VERSION` bump is a purely local reset, not a data-loss event for cloud-synced reps. `version` itself is never sent to Firestore; only `prices`/`targetCounts`/`callfile`/`cashCarry` are (see below).

**Cloud sync (Firebase)** — each rep has their own Firebase Authentication account (email/password, self-service signup on [login.html](login.html)/[js/auth.js](js/auth.js)) and their own Firestore document at `users/{uid}`, holding exactly the *persisted* slice of state — `{ prices, targetCounts, callfile, cashCarry }` — the same fields already described above as "persisted across resets." Session-only state (`productsSession`, `ppSession`, `callfileSession`) never leaves the device, same as before Firebase existed.
- **Design goal**: keep every existing page script (`products.js`/`partnership.js`/`callfile.js`) completely synchronous and untouched. `localStorage` remains the only thing `Storage.loadState()` reads, so `render()` still works exactly as it always has, including fully offline. Firestore is purely a background mirror underneath it, added in [js/cloud-sync.js](js/cloud-sync.js) and two small hooks in [js/storage.js](js/storage.js).
- **Writes**: `saveState()` (the one choke point every `Storage.set*`/`import*`/`log*`/`save*` mutator already funnels through) now also calls `window.CloudSync.pushState(state, callfileChanged)` — fire-and-forget from `storage.js`'s point of view (`.catch`'d to `console.error` rather than surfaced to the rep, since a failed background sync shouldn't block them from continuing to work locally), but internally `cloud-sync.js` chains every push onto a single `pushChain` promise rather than firing `setDoc` calls independently. This matters specifically for a Platinum store: it's the only grade where a rep logs two visits for the same store close together (Gold/Silver only ever need one), which fires two unawaited writes seconds apart — over patchy in-store wifi, without chaining, the *older* 1-visit write can arrive at Firestore *after* the newer 2-visit one and silently overwrite it, since the server just applies whichever write it receives last regardless of timestamp. Chaining guarantees the 2nd write's network request isn't even sent until the 1st has finished, so Firestore always receives them in the order they actually happened. `callfileChanged` is an optional bool the specific mutation passes when it touched `callfile` (e.g. `logVisit`/`addStore`/`deleteStore`/`importCallfile`/etc. all pass `true`; `setPrice`/`toggleChecked`/etc., which never touch the call file, pass nothing). `pushState` always pushes `prices`/`targetCounts`/`cashCarry` in full — `cashCarry` needs no such gate since `Storage.saveCashCarryDraft()` always overwrites the entire object wholesale (there's no per-key deletion hazard a stale device's push could cause, unlike `callfile`'s per-store map) — and only ever includes `callfile` in the write when `callfileChanged` is true — but when it does, it pushes the *entire* `state.callfile` object (not a per-store patch), written with `setDoc(ref, payload, { mergeFields: [...] })`. `mergeFields` (naming which top-level fields the payload provides) is what keeps this safe on two fronts at once: it leaves `prices`/`targetCounts` untouched when only `callfile` changed (and vice versa), while still replacing the *entire* `callfile` field with exactly what's given — including dropping any store key no longer present locally — rather than `{merge: true}`'s recursive deep-merge, which would leave a locally-deleted store's key alive forever on the server.
- **Offline write durability**: `firebase-config.js` initializes Firestore with `persistentLocalCache` (IndexedDB, multi-tab manager), falling back to the in-memory cache if the browser refuses IndexedDB. A `setDoc` made while offline is queued durably and replayed by the SDK when the connection returns, *even if the rep closed the app in between* — before this, the queue lived only in page memory, so an offline visit logged and then a closed tab meant the write silently never happened (localStorage still had it, Firestore didn't until some later unrelated mutation pushed the whole call file again). As a second net for the cases persistence can't cover (IndexedDB unavailable/evicted), `hydrateAndSubscribe` compares the local `callfile.updatedAt` against the cloud's *before* hydrating and, if local is newer, pushes it up (`pushState(state, true)`) right after — otherwise nothing would ever re-send it until the next mutation.
- **Sync status**: `window.CloudSync.status` (`{ state: "idle"|"saving"|"synced"|"error", pending, lastError, lastSyncedAt }`) is updated around every chained push and on hydration failures, and each change fires a `cloud-sync-status` event on `window`. `nav.js`'s `renderSyncStatus()` shows it as a one-line `.rep-sync` indicator under the rep's email ("Saving…" / "Synced" / amber "Not synced — check your connection"), plus "Offline — changes saved on this device" straight from the browser's `online`/`offline` events (an offline `setDoc` never rejects, it just stays pending, so `navigator.onLine` is the only timely signal). Purely informational, nothing persisted. `rerenderIfPossible()` wraps the page's `render()` in `try/catch` so a render bug surfaces as that bug rather than as a misleading "Could not load your saved data" rejection of the Firestore promise it runs inside.
- **Reads / hydration**: on load, `cloud-sync.js` waits for Firebase auth state (redirecting to `login.html` if signed out — this is the auth guard). `deck.html`/`pp-deck.html` have no rep state to sync and don't load `storage.js`/`cloud-sync.js`, so they use the tiny [js/auth-guard.js](js/auth-guard.js) instead — same redirect, nothing else — so no app page is reachable signed-out. Before touching Firestore at all, `hydrateAndSubscribe(uid)` checks `Storage.getOwnerUid()` against the signed-in `uid` — see "Local cache ownership" below — and wipes the device's local cache first if they don't match, so a different rep's data can never be read as "this account's data" by anything that follows. It then `getDoc`s the rep's `users/{uid}` doc once. If it exists, `Storage.hydrateFromCloud(cloudDoc)` writes `prices`/`targetCounts` straight from the cloud doc into the local blob (bypassing `saveState()`/`pushState()` — this data came *from* the cloud, echoing it back would be pointless), stamps `Storage.setOwnerUid(uid)`, and, since this all happens asynchronously after the page's first synchronous `render()` has already run once against whatever was locally cached, calls the page's global `render()` again (`typeof window.render === "function"`) so the UI catches up. It then opens a live `onSnapshot` listener on the same doc (skipping events where `metadata.hasPendingWrites` is true, since those are just this tab's own writes echoing back) so a second device's changes show up without a manual refresh.
- **First login** (`users/{uid}` doesn't exist yet): if `Storage.hasSavedData()` says this device already has a local blob, `confirm()` before adopting it as the new account's starting point; otherwise (or if declined) the account starts from `Storage.defaultPersistedSlice()` — the same defaults a brand-new device would have. Either way, a successful init stamps `Storage.setOwnerUid(uid)` too.
- **Local cache ownership**: `diageoPresenter` is device-level, not account-level (see "Design goal" above — every page's `render()` has to stay Firebase-independent), so nothing about the key itself says which rep it belongs to. A second small key, `diageoPresenterUid` (`Storage.getOwnerUid()`/`setOwnerUid()`), tags whichever account last hydrated into it. This exists because the device-level blob used to leak across accounts in two ways: (1) signing up for a brand-new account on a device that already had a different rep's data cached made `handleFirstLogin`'s `hasSavedData()` check true unconditionally, offering — and, if the confirm dialog was clicked through without reading it, actually performing — an "import" that permanently seeded the new account's Firestore doc with the old rep's data; (2) even for a *returning* rep, `hydrateFromCloud()`'s callfile conflict resolution (below) picks whichever side has the newer `updatedAt` with no owner check, so a different rep's very-recently-touched local cache could out-date-stamp the correct rep's real cloud callfile and win, and a later mutation would push that foreign callfile up to the correct account. `hydrateAndSubscribe`'s owner-mismatch wipe (above) closes both: a *foreign*-tagged cache is gone before either check ever runs. A cache with **no** tag at all (true for every device before this existed, and never re-triggered once tagged) is left alone rather than treated as foreign, which is what preserves the legacy one-time "adopt this device's pre-Firebase data" recovery case `handleFirstLogin` still supports. [js/nav.js](js/nav.js)'s logout handler also calls `Storage.clearLocal()` (wipes both keys, persisted *and* session state) before signing out, as a belt-and-suspenders good-hygiene measure — the owner tag already stops permanent contamination, but this also removes the brief stale-data flash the next signed-in rep would otherwise see before hydration completes.
- **Isolation**: enforced by [firestore.rules](firestore.rules). A rep can read/create/update/delete only their own `users/{uid}`; writes are shape-checked — `create` must contain only the seven known top-level keys (`prices`/`targetCounts`/`callfile`/`cashCarry`/`ccLocations`/`repTerritory`/`repEmail`), `update` may only *change* keys in that set (`diff().affectedKeys().hasOnly(...)`, so a doc still carrying some legacy top-level field from an older client isn't locked out of every future save), and `repEmail`, whenever written, must equal `request.auth.token.email` (the manager dashboard displays it, so it must not be forgeable). `pushState`'s payload and `handleFirstLogin`'s initial doc must stay inside that key set. Manager accounts (`managers/{uid}` marker docs) get read-only access to every `users/{uid}` — see "Manager area" below. There's no shared/team data; every rep's data is theirs alone, matching the fully-private-per-rep decision this was built around. Covered by a rules unit-test script (`@firebase/rules-unit-testing` against the emulator): cross-rep read/write denied, extra keys denied, forged `repEmail` denied, legacy-field docs still updatable, manager create fails closed without the config doc / with a wrong code / with a forged email, manager can read but not write rep docs.
- **Conflict handling** for `prices`/`targetCounts`/`cashCarry` is last-write-wins (whichever `setDoc` lands on Firestore last simply overwrites those fields) — a deliberate simplification, acceptable because data is private per rep (no simultaneous multi-user editing of the same doc to reconcile), not because it's the "correct" general solution. `callfile` uses the same last-write-wins idea, just gated on its own single `callfile.updatedAt` timestamp (bumped by every store mutator: `logVisit`/`resetVisits`/`resetAllVisits`/`addStore`/`updateStore`/`deleteStore`/`importCallfile`/`savePPSnapshot`) rather than the top-level fields' implicit "whichever write landed last" — `Storage.hydrateFromCloud()` compares `state.callfile.updatedAt` (local) against the incoming `slice.callfile.updatedAt` and adopts the incoming `callfile` *wholesale* only if it's at least as new; otherwise local is left alone (a rep can navigate to another page, or switch browsers, before a just-made change like logging a visit has actually finished pushing to Firestore — without this, the next page's own hydration read could race that in-flight write and roll the visit back). Every callfile saved before `updatedAt` existed lacks the field entirely (`undefined`, not `""`) — `hydrateFromCloud()` treats "neither side has one" as nothing-to-compare and leaves local alone rather than a bare `"" >= ""` string comparison, which would (and initially did) make the cloud unconditionally win on *every* hydration until some mutation finally stamps a real timestamp on either side, permanently masking whatever the fix itself changed. The one exception is a genuinely fresh device with no locally-cached stores at all, which has nothing to lose by adopting the cloud's copy even if it's also unstamped — the normal first-sync case. Earlier versions of this tried a *per-store* merge (each store keeping its own `updatedAt`, deletions written as tombstones so a stale read couldn't resurrect them) to let two devices' *different* stores merge without either clobbering the other — in practice this was a recurring source of bugs (a store rendered from a hybrid of an old cloud copy and a newer local one), so it was replaced with the simpler whole-`callfile` swap described above. The accepted tradeoff: if two sessions (e.g. this app open in both Chrome and Safari on the same phone) each edit a *different* store within the same few seconds, before either has synced, the one that pushes second wins outright and the other's edit is lost — including a store deletion: a stale session that still has a since-deleted store cached locally and pushes for an unrelated reason (e.g. logging a visit elsewhere) will resurrect it, since the whole `stores` map goes out together. Acceptable because actual usage is one rep working in one browser/device at a time (each page load re-hydrates from Firestore before any mutation can happen, which is what keeps this rare in practice), not simultaneous editing across two. `Storage.liveStoreKeys(stores)`/`Storage.getLiveStore(stores, key)` are still the two helpers every consumer (`callfile.js`, `map.js`, `partnership.js`'s store picker, `home.js`) reads `callfile.stores` through — now thin wrappers with no tombstone-filtering to do, kept so those call sites didn't need to change.

**Page scripts** ([js/products.js](js/products.js), [js/partnership.js](js/partnership.js), [js/callfile.js](js/callfile.js)) each follow the same pattern: a pure `render()` that reads `Storage.loadState()` and the relevant layout/catalog to rebuild the DOM from scratch (via `innerHTML` string templates, not diffing), plus a single delegated click listener per container keyed off `data-action`/`data-id` attributes. There's no framework — every UI update goes through a full `render()` call.

**Poster-matched theme (Partnership Program)** — `partnership.js`'s `render()` also sets `#tier-hero-img`'s `src` from a `HERO_IMAGES` map to show that tier's poster image, and sets `#tier-panel`'s class to `theme-silver` (Tier 3/1) or `theme-gold` (Tier 2). `css/styles.css` reads those theme classes to color the `.category` bands so the checklist visually matches the poster shown above it.

**Core Range gating (Partnership Program)** — Core Range is the mandatory "must stock" baseline, so a tier can't reach its reward threshold on Bonus/Premium items alone. `coreStats()` in `partnership.js` finds the section with `isCore: true` and checks whether every item in it is ticked; `tierStats()` folds this in as `pct = gatesComplete ? realPct : Math.min(realPct, 89)` — the displayed percentage itself is capped at 89%, not just the celebration badge, whenever a gate is incomplete. The Core Range `<h3>` also gets a live `.core-status` tag (amber `checked/total`, or green "✓ Complete") so the rep can see what's blocking the reward. This has no persisted state — it's pure derived math from `ppSession.checked`, recomputed on every `render()`.

**Reward unlock threshold (Partnership Program)** — Tier 1 and Tier 2 unlock their reward at 90%+ of the required count (`realPct >= 90`, on top of the gates above). Tier 3 instead unlocks at an **absolute count** — `unlockCount: 20` (of 23) in `layout-pp.js` — because 90% of 23 rounds up to 21, which is stricter than the intended "20 of 23" rule. `tierStats()` computes `unlocked` from whichever rule the tier's `unlockCount` field implies, and `render()` builds the `tier-reward` line's "at X" wording (`"20 of 23"` vs `"90%+ of 25"`) and drives the celebration badge (`isCelebrating = stats.unlocked`) from the same flag, so the two tier types can't drift apart. A tier without `unlockCount` always falls back to the 90% rule.

Gating isn't limited to "100% of Core Range" — a section can instead carry `gate: { groups: [{ label, items, min }, ...] }` for a partial (N-of-M) requirement, checked by `sectionGateStats()`. Currently only Tier 3's Bonus Range uses this: at least 2 of its 4 "bottle" items AND 1 of its 2 "crush" items must be ticked, on top of (not instead of) Core Range being 100% stocked — `tierStats()`'s `gatesComplete` ANDs every section's gate (isCore or quota-based) together. `gateTagHtml()` renders whichever tag applies per section (Core Range's is-core tag, or a quota section's `label checked/total` breakdown), and `gateSummaryText()` builds the `tier-reward` line's parenthetical from the tier's actual gates so it can't drift out of sync with `layout-pp.js`.

**"Jump to Core" display (Partnership Program)** — a section with `promoteOnCheck: true` (every tier's Bonus Range/Premium Spirits sections) visually promotes its ticked items into the Core Range section instead of leaving them in place: `sectionItemsToRender()` hides checked items from their own `promoteOnCheck` section and `jumpedItems()` appends them into the Core Range section's render list, tagged with a small "Bonus" badge (`isJumped` in `tileHtml()`). This is **purely cosmetic** — `coreStats()`/`tierStats()`/`gateTagHtml()` still read only the section's fixed `items` list, so the Core-100% gate always means exactly the 17 `CORE_RANGE_TIER3` products no matter what's ticked elsewhere. Unticking a jumped item sends it back down to its original section on the next `render()`. A `promoteOnCheck` section that empties out (everything jumped) is skipped entirely by `sectionHtml()` (returns `null`, filtered out) rather than showing a bare header. `Storage.selectAllTier()` bulk-ticks every item in the active tier at once (the "Select all" button, confirmed via `confirm()` since there's no per-tier undo — only the all-tiers Reset).

**Product zoom modal (Partnership Program)** — tapping a tile anywhere outside its "In stock" tick row (via `#tier-sections`'s delegated click listener falling through to `.pp-tile` when `.tick-row` doesn't match) calls `openProductModal(id)`, which sets in-memory `ppUi.zoomId` and re-renders. `renderModal()` (called at the end of every `render()`) shows/hides `#product-modal` and fills it from `window.CATALOG` plus a local `casePriceFor()`/`formatMoney()` (small copies of `products.js`'s helpers, always reading the Booker price, since `products.js` isn't loaded on this page). Closes via the × button, tapping the backdrop, `Escape`, or switching tiers (`ppUi.zoomId` is reset alongside `ppUi.wasAbove90` in the tier-tab click handler). `ppUi.zoomId` is session-only UI state, never persisted.

**Tier gating/stats math ([js/pp-stats.js](js/pp-stats.js))** — `coreStats`/`sectionGateStats`/`tierCheckedCount`/`tierStats`/`tierCheckedIds` used to live only in `partnership.js`, hardwired to read `state.ppSession.checked[id]`. They're now in this shared file as `ppCoreStats`/`ppSectionGateStats`/`ppTierCheckedCount`/`ppTierStats`/`ppTierCheckedIds` (exposed as `window.PPStats`), parameterized on an arbitrary checked-id `Set` instead — the same "shared logic, page-local orchestration" split as `js/callfile-status.js`, needed because Call File/Map's range-snapshot editor (below) requires the identical math against a frozen snapshot's `checkedIds` or an in-progress edit buffer, not the live session map. `partnership.js` keeps its original function names/signatures as thin wrappers that build a `Set` from `ppSession.checked` and delegate — zero behavior change for the live Partnership Program page. `window.PPStats.buildSnapshot(tierKey, checkedIds, targetCount, dateStr)` is the one place a `ppHistory`-shaped snapshot object (`{date, tierKey, checkedIds, checkedCount, target, pct, unlocked}`) gets constructed, used both by Partnership's save flow and by the range-snapshot editor. Loaded on all three of `partnership.html`/`callfile.html`/`map.html`.

**Save range to Call File (Partnership Program → Call File)** — the "Save to Call File" button lets a rep freeze the current tier's checklist state onto a specific store, so it can be reviewed later from Call File. There's no notion of "which store you're currently at" anywhere else in the app (Products/Partnership are just a global session), so saving always goes through a store picker: `openStorePicker()` sets `ppUi.storePickerOpen` and `renderStorePicker()` shows `#store-picker-modal`, a searchable list built the same way as Call File's own store search. Tapping a store calls `window.PPStats.buildSnapshot(tierKey, tierCheckedIds(tier, state), stats.target, todayISO())` and passes the result to `Storage.savePPSnapshot(key, snapshot)`. `ppSession` itself is untouched by saving (non-destructive, no auto-reset). `savePPSnapshot()` `unshift`s onto that store's `ppHistory` array and slices to the 2 most recent (newest first) — deliberately capped, not unlimited history. `Storage.importCallfile()` carries `ppHistory` forward from the prior record on re-upload, the same way it already does for `visits`, so re-uploading a call file export doesn't wipe saved ranges.

**Range snapshot editor (Call File + Map)** — a store card's (Call File) / map popup's (Map) "Range" button is now **always shown**, regardless of `ppHistory.length` — previously it was hidden until a range had been saved from Partnership Program at least once. Tapping it calls `openRangeModal(key)`, which sets `callfileUi`/`mapUi`'s `rangeKey`/`rangeIndex` (plus `rangeEditing`/`rangeEditChecked`/`rangeNewTier`, all session-only UI state, never persisted) and shows `#range-modal`. Three states, all driven by `renderRangeModal()`:
- **Read-only** (`history.length > 0`, not editing): up to 2 tappable date tabs plus a detail pane built by `window.PPSnapshot.sectionsHtml(tierKey, checkedIds, { editable: false })` ([js/pp-snapshot.js](js/pp-snapshot.js)) — walks `window.PP_LAYOUT[snapshot.tierKey].sections` and renders each section's fixed `items` list, deliberately **not** replicating the "jump to Core" promotion (`promoteOnCheck`) since that's a live-editing cosmetic feature a frozen historical view doesn't need. An **Edit** button here calls `startRangeEditExisting(snapshot)`, seeding the edit buffer from that snapshot's `checkedIds`.
- **Editing an existing snapshot** (`history.length > 0`, editing): the same sections render via `{ editable: true }` instead — real checkboxes (`ppEditableTileHtml`, modeled on `partnership.js`'s `tileHtml`) wired to `data-action="range-toggle"`, plus each section's live gate tag computed through `window.PPStats`. **Save** calls `Storage.updatePPSnapshot(key, rangeIndex, snapshot)` — a new storage mutator (sibling to `savePPSnapshot`) that overwrites `store.ppHistory[index]` **in place**, deliberately preserving the original snapshot's `date` (this is an edit of the same saved range, not a new dated entry). **Cancel** discards the edit buffer and reverts to the read-only view.
- **No saved range yet** (`history.length === 0`): instead of hiding the button, the modal shows a tier picker (`Object.keys(window.PP_LAYOUT)`) so a rep can start a range **from scratch** without ever visiting Partnership Program. Picking a tier (`startRangeNewTier(tierKey)`) opens the same editable checklist, starting fully unchecked. **Save** here goes through the original `Storage.savePPSnapshot(key, snapshot)` (append, not update), since an empty `ppHistory` naturally lands the new entry at index 0.

Both `js/callfile.js` and `js/map.js` implement this identically (mirrored `rangeEditing`/`rangeEditChecked`/`rangeNewTier` state and the same `selectRangeTab`/`startRangeEditExisting`/`startRangeNewTier`/`toggleRangeChecked`/`cancelRangeEdit`/`saveRangeEdit` functions) — Map's versions call `renderRangeModal(Storage.loadState())` directly rather than the page's full `render()`, same as before this feature, to avoid disturbing Leaflet's marker layer/pan-zoom state. `js/pp-snapshot.js` is loaded on `callfile.html`/`map.html` only (not `partnership.html`, which keeps its own live tile renderer with the jump-to-core cosmetic this bounded editor doesn't need).

**Call File** ([js/callfile.js](js/callfile.js), [callfile.html](callfile.html)) — lets a rep upload their call-file export (`.xls`/`.xlsx`/`.csv`, parsed client-side via the vendored [js/vendor/xlsx.full.min.js](js/vendor/xlsx.full.min.js) — SheetJS 0.20.3 from `cdn.sheetjs.com`, since there's no package manager to pull it in another way; 0.18.x had a prototype-pollution and a ReDoS CVE, so don't downgrade) and track monthly visit compliance per store.
- Only `OUTLETNAME` / `OUTLETGRADE` / `POSTCODE` are read from the sheet; everything else (DIAGEOID, FREQUENCY, VISITCADENCE, TERRITORY, ...) is ignored by design.
- Stores are keyed by a normalized `name|postcode` string (`Storage.storeKey`), not a spreadsheet id — re-uploading a later export matches existing stores by that key and keeps their visit history. Duplicate rows sharing name+postcode within one upload collapse to a single store (last row in the file wins); there's no DIAGEOID to tell a true duplicate apart from two different accounts that coincidentally share a name+postcode, so `Storage.importCallfile` reports how many rows collapsed (`duplicateCount`) rather than silently guessing.
- Status colour is *derived at render time*, never stored: `storeStatus()` (in [js/callfile-status.js](js/callfile-status.js), shared with `map.js` — see Map below, rather than living privately in `callfile.js`) counts how many dates in a store's `visits` array fall in the current calendar month and compares against `CALLFILE_GRADE_CONFIG[grade].visitsRequired`. This is what makes the "every store goes back to red at the start of a new month" behavior automatic — there's no reset job, it just falls out of the date math. Visits are never deduped by date (`Storage.logVisit`), since a Platinum store can legitimately be visited twice in one day and both must count.
- The grade tabs (Platinum/Gold/Silver, one visible at a time) are a UI-only filter — `callfileSession.activeGrade` just controls which pre-computed group is rendered.
- **Store list UI** — `.store-list` is a bordered, internally-scrolling panel (`max-height` + `overflow-y: auto`) rather than an unbounded page section, so a large call file doesn't turn the page itself into one long scroll. Each `.store-card` is a compact two-line layout (`storeRowHtml()`): name + status pill on top, postcode/last-visit/next-visit + the "Log visit" button on the bottom. `statusLabel()` and the dates (`formatDateShort()`, no year) are deliberately terse to fit that one line without wrapping.
- **Log-a-visit date picker** — tapping "Log visit" no longer logs `todayISO()` immediately; it calls `openVisitModal(key)`, which sets in-memory `callfileUi.logKey` and re-renders to show `#visit-modal` (same `.modal-backdrop`/`.modal-card` pattern as the PP product modal) with a native `<input type="date">` defaulted to today and capped (`max`) at today so a rep can't log a future visit, but *can* back-date a forgotten visit. `renderVisitModal()` (called at the end of every `render()`) just shows/hides the modal and fills in the store name — it never touches the date input's value, so an in-progress date pick survives re-renders. Confirming reads the input's value and calls `Storage.logVisit(key, dateVal, cfg.cadenceWeeks)` with that chosen date instead of today's. Closes via the × button, backdrop click, `Escape`, or Cancel, all funneling through `closeVisitModal()`. `callfileUi.logKey` is session-only UI state, never persisted.
- **Visits-by-date filter** — a "Visits by date" button under the search bar answers the opposite question to the status grouping: not "where does each store stand this month" but "what did I actually do on a given day". It opens `#date-filter-modal` (same pattern as the log-a-visit picker above — native `<input type="date">`, `max` capped at today so only past dates are pickable, value set *after* `render()` so a pick survives re-renders) and sets `callfileUi.filterDate`. While that's non-null, `render()` swaps `#callfile-sections`'s content from `gradePanelHtml()` to `dateFilterPanelHtml(entries, dateStr)`, which keeps only stores with that date in their `visits` array, sorts by name, and reuses the **existing `storeRowHtml()`** — so the rows keep their live Log visit/Range/CB/Edit buttons rather than being a read-only copy. `storeRowHtml()` gained an optional third `visitCount` arg for this, rendering a `×N` badge when a store was visited more than once that day (`Storage.logVisit` deliberately never dedupes by date, so a Platinum store genuinely can be); every other call site omits it. Because `render()` applies the grade tabs and the search box *before* this branch, both keep narrowing *within* the chosen date for free. A `data-action="clear-date-filter"` button in the heading (handled by the same `#callfile-sections` delegated listener as the row actions) returns to the normal red/amber/green grouping. Entirely derived at render time from data `logVisit` already stores — `filterDate`/`dateModalOpen` are session-only in-memory UI state like `logKey`, so nothing new is persisted, no `SCHEMA_VERSION` bump, and nothing extra syncs to Firestore.

**Map** ([js/map.js](js/map.js), [map.html](map.html)) — plots every Call File store with a postcode as a pin on a real, pannable UK map, colored by the same `storeStatus()` red/amber/green rule Call File uses (they share [js/callfile-status.js](js/callfile-status.js) — `todayISO()`/`storeStatus()`/`statusLabel()` were extracted out of `callfile.js` into that file specifically so this page and Call File can't drift on the business rule). `callfile.js` itself is *not* loaded on `map.html` — its `DOMContentLoaded` handler assumes callfile.html's DOM (`#store-list` etc.) exists, so map.js only pulls in the shared status file plus `layout-callfile.js` for `CALLFILE_GRADE_CONFIG`.
- **Map library** — Leaflet is vendored locally at `js/vendor/leaflet/leaflet.js`/`leaflet.css` (same treatment as `js/vendor/xlsx.full.min.js`), tiles are fetched at runtime from OpenStreetMap and are deliberately *not* in `PRECACHE_URLS` (cross-origin, dynamic per pan/zoom — same opportunistic-cache-only tradeoff already accepted for the Firebase SDK). Markers are `L.circleMarker`s (colored SVG dots via `fillColor`), not Leaflet's default image-based `L.Icon`, so no marker-icon PNGs need vendoring.
- **Geocoding** — postcodes are raw, unvalidated strings straight off the uploaded sheet (`callfile.js`'s `parseWorkbook()`), so `map.js` geocodes them at runtime via the free, no-key **postcodes.io** bulk endpoint (`POST https://api.postcodes.io/postcodes`, chunked into batches of 100 — its per-request limit) and caches both hits and misses (`{found:false}`) in a **separate** localStorage key, `diageoGeocodeCache` — deliberately *not* part of the schema-versioned `diageoPresenter` blob, since geocoded coordinates are derived reference data, not private per-rep state, so they don't need a `SCHEMA_VERSION` bump or Firestore sync. The cache key is the normalized postcode string itself, so a rep fixing a typo'd postcode in a re-uploaded call file automatically gets a fresh cache entry with no manual invalidation.
  - **Cache save race** — `render()` runs multiple times per page load (initial `DOMContentLoaded`, post-hydration, `onSnapshot` echoes), and each run that finds missing postcodes does its own independent load-cache → fetch → save-cache cycle. Two of these can overlap; the fetch that resolves *last* used to save whatever snapshot of the cache *it* loaded at the start of its own render() call, blindly overwriting localStorage — silently discarding any newly-geocoded postcodes the other cycle had just written in the meantime. This is what made a random, different subset of otherwise perfectly valid stores disappear from the map on every reload (not a network failure — a lost update between two concurrent cache saves). The `.then()` handler now re-`loadGeocodeCache()`s immediately before merging in its results and saving, so it always merges onto whatever is currently persisted rather than a stale snapshot — verified with a Node harness driving two overlapping render() calls with out-of-order-resolving fetches (fails on the pre-fix code, passes after) and, separately, an 18-store real-postcodes.io browser run reloaded 6 times in a row (was flapping between 17-18 markers depending on race timing; now identically 18/18 every time).
- **Re-render safety** — `render()` is called on `DOMContentLoaded` and, since it's an implicit `window.render` (a top-level classic-script function declaration, same as every other page's `render()`), also by `cloud-sync.js`'s post-hydration/`onSnapshot` re-render hook. Three module-level `mapState` flags make repeat calls safe: `ensureMap()` no-ops after the first `L.map()` call (Leaflet throws if you initialize the same container twice), `hasFitBounds` stops the view from re-centering after the rep has already panned/zoomed, and `inFlightPostcodes` dedupes concurrent geocode requests for the same postcode.
- **Co-located stores** — postcodes.io geocodes to a postcode's centroid, not an exact address, so stores that share a postcode (a shopping parade, e.g.) resolve to the *exact same* coordinate. Left alone, `L.circleMarker`s just stack on top of each other: only the one drawn last is visible/clickable, the rest are perfectly hidden underneath — not missing data, just visually and interactively unreachable, and since it's whichever store happened to be drawn last, which one "wins" can look like it changes across reloads even though nothing about the underlying data did. `plotMarkers()`'s `offsetForIndex()` groups entries by their rounded geocoded coordinate and, for any group with more than one store, spreads its members around a small fixed-radius circle centered on the true point (`entries` is pre-sorted by store key in `collectStoreEntries()`, so each store's position within its group — and therefore its offset direction — is stable across reloads, not dependent on `Object.keys()` iteration order, which isn't guaranteed to survive a Firestore round-trip). The radius (kept well under ~150m) is a deliberate balance, not a tuned-to-look-nice number: big enough that co-located stores are individually tappable once a rep zooms to a normal interacting level, but small enough to not bleed into a *different*, unrelated postcode's cluster — dense urban postcodes can be barely 150-200m apart in reality (e.g. CR0 0JB to CR0 0JD, from this app's own reported bug, is ~170m). Like any map of closely-spaced points (this one or Google/Apple Maps alike), co-located stores still visually overlap at the widest possible zoom-out — that's an accepted limit, not a bug — and cleanly separate once zoomed in.
- **Page-zoom trap / touch handling** — Leaflet sets `touch-action: none` on `.leaflet-container`, so the browser performs *no* default touch behavior over the map: no page pan, no page pinch-zoom. Since the map fills essentially the whole viewport, a rep whose *page* (visual viewport) zoom drifted above 1 had nowhere left to pinch back out from, and `.rep-sidebar` — laid out in the layout viewport — sat off-screen: the map still worked, but no other page was reachable without closing and reopening the app. Reported from the field while tapping the Cycle Brief modal's `+`/`−` steppers, which is the app's most reliable way to trigger double-tap-to-zoom. Two halves fix it, and both are needed: `css/styles.css`'s global `touch-action: manipulation` on interactive elements (`button, a, label, input, select, summary, .tick-row`) stops a tap from ever zooming the page — deliberately global, since Products' steppers and Partnership's tick rows share the hazard, and deliberately *not* on `.leaflet-container` — and [js/map-zoom-guard.js](js/map-zoom-guard.js) (`window.installPageZoomGuard()`, called from both `map.js` and `manager-map.js`'s `DOMContentLoaded`, loaded only on the two map pages) watches `visualViewport` and snaps the page back to scale 1 if it drifts anyway. The guard pulses `maximum-scale=1` onto the viewport meta for two frames and then removes it, rather than leaving it there — pinch-zoom keeps working, it just can't get stuck. Note `maximum-scale`/`user-scalable=no` in the `<meta>` itself is *not* a fix: iOS ignores both, which is why `touch-action` does the real work. `.locate-btn`'s `z-index` is also pinned below `.modal-backdrop`'s 60 (it was 1000, i.e. painting above every modal — nothing in `main.map-page`/`.rep-main` creates a stacking context to contain it). That one was fixed on principle, not as a repro: no modal control actually falls under the button at the viewport sizes checked, since the cards are centred and their buttons clear the bottom-right corner.
- **Map page sizing** — `map.html`/`manager-map.html` carry `<body class="page-map">`, which makes the shell a `100dvh` (with a `100vh` fallback) flex column with `#map-container` as `flex: 1`. This replaced a per-shell magic number (`calc(100vh - 90px)`) that assumed a fixed-height nav: below 720px the sidebar becomes a top bar whose six links wrap onto a second row, so the page ran taller than the screen — and because of the `touch-action: none` above, the only surface left to scroll that overflow back was the top bar itself. `100dvh` also keeps iOS's collapsing browser chrome from pushing the bottom of the map out of view.
- **Status colors** are read from `--good`/`--warn`/`--bad` via `getComputedStyle` at map-init time rather than hardcoded — Leaflet's SVG renderer sets `fill` as a raw attribute, which can't resolve `var(--good)` directly, so this keeps the map palette tied to Call File's pill/dot colors without a second copy of the hex values.
- Tapping a pin shows a read-only popup (name/grade/postcode/status/last & next visit) — no "log a visit" action from the map; that stays on Call File. Map has no tab UI of its own; instead `collectStoreEntries()` filters by `state.callfileSession.activeGrade` — the same session-only value Call File's own grade tabs write to via `Storage.setCallfileGrade()` — so whichever tab (All/Platinum/Gold/Silver) was last active on Call File is exactly what Map plots. "All" (Call File's 4th tab, alongside the original three) shows every grade at once with the shared status legend.

**Cash & Carry Form** ([js/cashcarry.js](js/cashcarry.js), [cashcarry.html](cashcarry.html), [js/layout-cashcarry.js](js/layout-cashcarry.js)) — a native in-app replica of an external Microsoft Form ("Cash & Carry Stock Availability Convenience", at the URL linked from the page's "Open official form" button) that a rep fills out on every C&C depot visit. The real form's schema was verified directly by loading it in a browser (all four "which C&C" branches — Bestway/Booker/Makro/Other — and both North/South regions show the identical 39-product list; only a couple of extra fields differ by branch), not guessed, so `layout-cashcarry.js`'s `CASHCARRY_PRODUCTS`/`CASHCARRY_STATUS_OPTIONS`/`CASHCARRY_CHAINS`/`CASHCARRY_REGIONS` can be trusted as accurate to the live form as of when this was written.
- **Single remembered draft, not a history** — `state.cashCarry` is one mutable object (`Storage.saveCashCarryDraft()` overwrites it wholesale on every Save), *not* an array of past visits like Partnership's `ppHistory`. Every field — including all 39 per-product stock statuses — pre-fills with whatever was last saved, until the rep changes it; there is no per-visit log and no per-C&C-chain scoping (picking a different chain doesn't reset or separately remember the others' answers).
- **Product ids are name-derived slugs, not array indices** (`CASHCARRY_PRODUCTS[i].id`, e.g. `"casamigos70cl"`) — so inserting or reordering a product in the list later can never silently shift another product's saved status onto the wrong id.
- **We cannot submit into the real Microsoft Form programmatically** — it's a separate, cross-origin system with no public API, and Microsoft Forms' prefill-link feature (where it exists) requires manually generating a link per fixed value combination from the form owner's editor, not something settable dynamically per rep/per visit. So the flow is: fill in the native form (39 `<select>` dropdowns, one per product, rather than replicating Microsoft's spread-out radio-button layout — matches this app's existing compact/mobile-first pattern), tap **Save answers** (writes `state.cashCarry` via `Storage.saveCashCarryDraft()`), then tap **Open official form**, which *also* saves first (belt-and-suspenders, so a rep who skips "Save answers" still has that visit's edits captured) before opening the real Microsoft Form in a new tab for the actual compliance submission — the rep re-picks the same answers there, fast since they're already decided.
- Conditional fields: picking **Other** as the chain reveals **"If other please state which"** (a plain visibility toggle, not destructive — the stored value survives even while hidden, so switching back to "Other" later still shows what was last typed). The North/South region question is **always** shown regardless of which chain was picked, matching the verified real-form behavior exactly.

**Nav/shell** — [js/nav.js](js/nav.js) injects a shared left-hand sidebar shell into every page and registers the service worker. It's loaded as the last script tag of each page as `<script src="js/nav.js" data-page="home"|"products"|"partnership"|"callfile"|"map"|"cashcarry"|"deck"|"ppdeck">` and calls `renderNav(document.currentScript.dataset.page)` itself — it used to be an inline `<script>renderNav("...")</script>`, which the page CSP now forbids (see "Running it"). The same `data-page` bootstrap applies to `js/manager-nav.js` on the two manager pages. It is the only place that knows the page list. Mirroring [js/manager-nav.js](js/manager-nav.js)'s manager sidebar, `renderNav()` builds a `.rep-shell` containing a `.rep-sidebar` (brand, nav links, and a `.rep-account` block with the rep's email + a "Log out" button) plus an empty `.rep-main`, moves every existing `document.body` child into `.rep-main`, then appends the shell — so the page's own markup ends up as the sidebar's flex sibling rather than sitting under a header. The email is filled in once `onAuthStateChanged` resolves (same `firebase-ready` handshake as everywhere else Firebase is used), since the sidebar renders before auth state is known. Below `max-width: 720px` the sidebar collapses into a horizontal top bar (same breakpoint/pattern as the manager sidebar). `login.html` doesn't call `renderNav()` at all — it isn't part of the app shell.

**Manager area** ([manager-login.html](manager-login.html) / [js/manager-auth.js](js/manager-auth.js), [manager-dashboard.html](manager-dashboard.html), [manager-map.html](manager-map.html), [js/manager-cloud.js](js/manager-cloud.js)) — a separate account type with read-only access to every rep's `users/{uid}` doc. A manager is any auth account with a `managers/{uid}` marker doc, and that marker can only be **created with the shared manager access code**, verified by the rules, not the client: the code lives in Firestore at `config/managerAccess` (field `code`), a doc no client can read or write, and the `managers/{uid}` create rule compares `request.resource.data.code` against it via `get()` (rules' `get()` bypasses client read permissions, which is what makes a server-enforced secret possible with no backend). `manager-auth.js` therefore holds no code constant at all: signup writes `{ email, createdAt, code }`, and on `permission-denied` it deletes the just-created auth account again (`deleteUser`, exported from `firebase-config.js`) and shows "That access code isn't valid." Two details keep that rollback reachable: the marker check (`isManager()` here, and `manager-cloud.js`'s gate) uses `getDocFromServer()`, never `getDoc()`, because Firestore's latency compensation makes a just-attempted, about-to-be-rejected write look like an existing doc in the local view (with the persistent cache, even across a navigation); and `onAuthStateChanged` — which fires the instant the auth account exists, before the marker write is accepted — skips its redirect while `signupInProgress` is set. Found by the end-to-end test: without both, a wrong code landed on the dashboard with a live auth account and no rollback. If `config/managerAccess` doesn't exist, `get()` yields null and the rule errors → create denied (fails closed), so **creating that doc in the Firebase console is a one-time manual setup step**; changing the code later is editing that doc, no redeploy. Accepted residual risk (a deliberate product decision): anyone who learns the code can self-register as a manager. `manager-cloud.js` surfaces a failed manager check / rep fetch in the page's empty-state element (`#manager-empty` / `#map-empty`) instead of leaving "Loading…" up forever.

**Offline support** — [service-worker.js](service-worker.js) precaches an explicit file list (`PRECACHE_URLS`, including product images, the `images/PP/tier-*.png` poster images, and the vendored xlsx library) on install; same-origin HTML/CSS/JS is network-first (2.5s timeout, then cache; an uncached navigation falls back to `./index.html`), everything else cache-first. **What may be cached at runtime is an explicit allowlist** (`isRuntimeCacheable`): GET requests that are same-origin, `www.gstatic.com/firebasejs/*` (versioned, immutable SDK bundles), or `*.tile.openstreetmap.org` (map tiles). Anything else — Firestore / Identity Toolkit / Secure Token API calls, postcodes.io — gets no `respondWith()` at all, so the browser handles it as if no service worker existed. This replaced a cache-first fallback that stored *every* non-app-shell GET it saw, including Firestore channel responses and 404 images, forever. Only successful responses are stored (`isStorable`: `response.ok`, or an opaque tile response), so a 4xx/5xx can never replace a good cached copy. On activate it deletes any cache not matching the current `CACHE_NAME`. Because of this, a browser that already has the app open needs a hard refresh (or full close/reopen if installed as a home-screen PWA) to pick up a new `CACHE_NAME` — bumping the constant alone doesn't update already-open clients. The Firebase SDK itself is fetched from `www.gstatic.com` at runtime and is *not* in `PRECACHE_URLS` (a cross-origin precache failure would fail the entire service worker install) — it's cached opportunistically by the same cache-first `fetch` handler after its first successful load, so a rep who's opened the app online at least once can still open it (and read their last-synced local data) offline; signing in for the very first time still requires a live connection.
